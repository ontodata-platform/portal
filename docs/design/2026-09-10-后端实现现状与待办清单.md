## 第一部分：现状（改后端前必读）

### 1.1 架构形态

- **单体聚合，不是微服务**：`server` 模块是启动器（`PortalApplication.java`），把 10 个 center 模块作为 jar 依赖装进同一进程，默认端口 **18085**（`SERVER_PORT`）。
- 技术栈：Spring Boot 3.3.13 + Java 21 + JPA + Flyway + MySQL + Kafka + OIDC Resource Server。
- 依赖外部 BOM `com.runisys.ontodata:ontodata-sdk-bom:0.1.0-SNAPSHOT`（sdk-events/sdk-web/sdk-security，源码不在本仓库）。
- 架构风格：**事件驱动（Outbox → Kafka → Inbox → 投影）+ 上游系统 REST 聚合**。

### 1.2 上游系统（三个，均已实现真实 HTTP 客户端）

| 上游 | 默认地址 | 用途 | 调用点 |
|---|---|---|---|
| 管理平台 data-platform | `127.0.0.1:18081` | 数据产品目录、订阅投递 | `MarketplaceService.java:48` |
| 算法转换工具 transform | `127.0.0.1:18082` | 能力目录 | `WorkbenchService.java:38-40` |
| 算法重组平台 recombine | `127.0.0.1:18083` | 算法运行 `/api/v1/executions` + `/start` | 同上 |

统一走 `aggregation-center/.../infrastructure/UpstreamHttpClient.java`（JDK HttpClient，5s 超时，透传 `X-Tenant-Id`）。
**既有约定：读失败降级（200 + `available=false` + 中文提示）；写失败抛 `UpstreamWriteException` → 502 `UPSTREAM_FAILED`。不得改成 200 降级写路径。**
探活：`UpstreamHealthIndicator` 对三者做 /actuator/health 探测。

### 1.3 认证与身份

- 无本地登录。`spring-boot-starter-oauth2-resource-server` + 外部 `sdk-security`；安全链见 `server/.../security/SecurityConfiguration.java`。
- IAM 开启时：JWT claims 是唯一身份事实来源（`tenant_id` 必填缺则 403；`org_id`/`project_id`/`clearance`/`portal_roles`），见 `OidcClaimMapping.java`、`ClaimContextFilter.java`；显式 `X-Tenant-Id` 头被忽略。
- IAM 关闭（`IAM_ENABLED=false`，当前默认）：`TenantContextFilter` 读请求头，身份回退固定 **`dev-user`**（`CurrentOperator.java:19`，启动打 WARN）。前端靠 `devMode=true` 展开全菜单。
- 授权：ABAC 引擎 `common/.../security/AbacPolicyEngine.java`，策略存 `portal_abac_policy` 表（V8 有 seed）+ TTL 缓存 + 内置默认回退。
- 示例 IdP：Keycloak `http://localhost:8180/realms/ontodata`（application.yml 注释）。

### 1.4 事件机制

- 写路径同事务落 `outbox_event` 表（`common/.../event/OutboxEventService.java`）→ `OutboxKafkaPublisher`（全库唯一 @Scheduled，5s 轮询、批量 100、幂等 ack）→ Kafka → `task-center` 的 `TaskProjectionEventListener`（@KafkaListener 订阅 6 个域主题）→ `portal_event_inbox` 幂等消费/乱序跳过 → 更新 `portal_task` 投影。
- `KAFKA_EVENTS_ENABLED=false` 可整体关闭（测试/演示环境）。
- 投影可回放重建：`POST /api/v1/projections/rebuild`。
- 既有约定：审批决定仍发 `portal.approval.decided` 给外部订阅方；门户自己的 DATA_GRANT 投递用同步 `@EventListener`（避免 approval↔aggregation 循环依赖，见 2026-08-27 文档 §2.1）。

## 第二部分：功能域覆盖对照（技术要求 vs 后端现状）

| 技术要求功能域 | 后端现状 |
|---|---|
| 智能问答 | ❌ 整域为零（无会话/消息/推荐/本体接口） |

| 算法服务 | 🟡 部分：能力目录/详情/运行提交（转发 recombine）+ 结果查看；**算法推荐/preflight 校验落库/任务复用 rerun-cancel/输入数据引用 = 无** |
| 个人中心 | 🟡 大部分：me、我的需求/申请、待办、站内通知；**个人资料维护/权限全景/收藏记录/下载记录 = 无** |

| 人员权限 | ❌ 整域为零（无用户/组织/权限 CRUD，仅 ABAC 判定引擎）。技术要求定位门户为"用户与组织权威管理中心" |

| 消息审计 | 🟡 站内通知+Outbox 作业有；**附件=无，操作审计表=无，定时清理=手动接口** |

## 第三部分：后端待办清单（按优先级）

> 约定：所有新表带 `tenant_id`（索引）+ 审计字段（created_by/created_at/...）；所有新接口进 ABAC；所有新域补 H2 集成测试（§1.7 基线）；错误协议沿用统一 `ApiError`（status/code/traceId/fieldErrors）。

### P0 —— 打通用户端主链路（数据申请→审批→交付→下载）

- **T0-1 结果下载/领取真实化**
  现状：`portal_result` 只有登记与查询元数据，没有文件流。前端"下载"是 toast。
  方案：新增交付文件存储（本地盘/NAS 路径或 MinIO），`portal_result` 加 `file_ref`/`file_name`/`size`/`checksum`；新增 `GET /api/v1/results/{sourceSystem}/{resultId}/download`（受控下载：校验申请已交付 + 权限 + 生成短期签名链接或直接流式返回）；下载动作写审计（见 T1-4）。
- **T0-2 数据工作台后端（前端契约已定，照单实现）**
  前端 `api/data-workbench.ts` 已约定（baseURL `/api/v1`）：
  `GET /datasets`（分页+筛选）、`GET /dataset-domains`、`GET /datasets/{code}`、`GET /my/applications`、`GET /my/data-subscriptions`。
  目录数据继续聚合 data-platform；"我的申请/订阅"可投影本地 `portal_approval_request`/订阅数据。响应 DTO 与 `src/api/data-workbench.ts` 的 TS 类型逐字段对齐。
- **T0-3 算法工作台后端（前端契约已定）**
  前端 `api/algorithm-workbench.ts` 已约定：
  `GET /algorithm-categories`、`POST /test-data`、`GET /algorithm-services`、`GET /algorithm-services/{code}`、`POST /algorithm-services/{code}/preflight`、`POST /algorithm-services/{code}/runs`、`GET /my/algorithm-runs`、`GET /my/algorithm-runs/{taskId}`、`POST .../rerun`、`POST .../cancel`、`GET /my/data-subscriptions`。
  运行仍转发 recombine `/api/v1/executions`；新增 `portal_algorithm_run` 表存提交参数/输入引用/状态镜像/结果引用（rerun/cancel 直接靠这张表，不再依赖前端 localStorage 草稿）；preflight 调 recombine 校验接口或按详情里参数元数据本地校验。
- **T0-4 演示数据 seed**
  新增 `V11__demo_seed.sql`（或 `R__demo_seed.sql` + 开关）：演示租户、公告 3–5 条、数据产品 8–10 个（含不同分类/更新周期）、走到不同状态的需求/申请/审批/任务/结果各若干、反馈若干。**所有演示数据必须带 `tenant_id`，且文档注明仅演示环境启用。**

### P1 —— 补齐要求内的整域缺口

- **T1-1 人员权限域（最大缺口；门户定位=用户/组织权威管理中心）**
  新表（草案）：`portal_user`（全局用户标识、账号状态、档案）、`portal_org`（组织树，parent_id、岗位）、`portal_user_org`（人员归属+生效时间）、`portal_portal_permission`（门户菜单/页面/按钮/接口/入口授权）、`portal_external_permission`（分系统权限非权威副本：角色、资源、有效期、授权来源、最近同步时间）、`portal_permission_request`（系统级权限申请，走审批）、`portal_reclaim_notice`（变更回收协同：发送状态/处理状态/失败原因/补办）。
  接口：用户/组织 CRUD+启停、权限分配、`GET /api/v1/iam/overview`（个人权限全景）、外部权限汇集查询、回收通知发起与状态跟踪。
  注意：与 ABAC 引擎的关系=门户权限表是策略的**管理面**，判定仍走 `AbacPolicyEngine`。
- **T1-2 审批配置（流程/表单/事项类型）**
  新表：`portal_approval_type`（事项类型字典）、`portal_approval_flow`+`_node`+`_node_role`（流程定义+版本）、`portal_form_def`+`_field`（表单 JSON Schema + 版本）。
  接口：类型/流程/表单 CRUD+版本管理；`ApprovalController` 创建时按类型解析流程。存量 DATA_GRANT 等枚举迁成字典数据。
- **T1-3 附件管理**
  新表：`portal_attachment`（业务类型+业务编码、文件名、存储 key、大小、上传人、有效期、清理时间）。
  接口：`POST /api/v1/attachments`（multipart）、`GET /{id}/download`（访问控制）、`DELETE /{id}`。申请/需求/审批实体加附件引用列表。到期清理挂定时任务（见 T2-3）。
- **T1-4 操作审计**
  新表：`portal_audit_log`（谁、何时、租户、动作、对象类型/编码、before/after 摘要、来源系统、traceId）。
  方案：AOP 切面或显式 `AuditRecorder` 挂到所有写路径 + 登录/访问事件；对外`GET /api/v1/audit-logs`（管理端查询，分页+筛选）。
- **T1-5 智能问答后端**
  前端契约 `api/agent.ts`（baseURL `/agent`，独立端口 **18087**）：`GET /defs`、`GET /defs/{id}`、`POST /sessions`、`GET /sessions/{id}`、`GET /sessions/{id}/messages`、`POST /sessions/{id}/confirm`、`POST /sessions/{id}/runs`、`GET /runs/{id}`、`GET /catalog/search`、`GET( SSE ) /sessions/{id}/stream`。
  最低实现：会话/消息两张表入库（个人中心"问答记录"才有数据源）；推荐先用"已发布目录关键词/语义检索 + 推荐卡（说明依据与限制）"；SSE 流式转发；确认卡（R4）落到对应表单预填接口。本体匹配/推理后续接算法重组软件已发布本体接口。

## 第四部分：实现顺序建议

1. T0-4（seed，半天级）→ 立刻消除"空"感，前后端联调有数据。
2. T0-2、T0-3（工作台两个后端，前端已写好 `viaMock` 一行切换）→ 前端切真实模式即可验收。
3. T0-1（下载）→ 主链路闭环。
4. T1-1 人员权限 → T1-2 审批配置 → T1-3 附件 → T1-4 审计 → T1-5 智能问答。
5. P2/P3 按运营与验收反馈排。
