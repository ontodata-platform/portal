# 需求管理业务闭环增强实施计划

**目标：** 将管理端“需求管理”从状态列表升级为可受理、可分析、可整合、可分派、可追踪的运营工作台；本轮以门户本地 mock 完整演示，真实接口缺口明确登记，后续联调替换即可生效。

**实现边界：**

- 不改变数据服务授权边界。相似数据需求可共用分析与交付工作，但每张原始需求单仍保留提出人、审批和授权记录。
- 只允许同租户、未终态、数据分类一致且用途不冲突的需求参与整合；管理员必须填写整合说明。
- 所有新增页面文字为中文；现有列表、筛选、详情、办理和关闭能力不回退。
- 本轮不要求启动容器或连接真实后端；mock 是可操作的临时权威，接口契约保留在本文末尾供联调使用。

## 本次落地状态（2026-09-09）

- 已完成：结构化数据需求受理、本地相似候选与用途/敏感等级约束、分析事实、主从整合关系、承接计划、进度记录和事实时间线。
- 已完成：个人端收回运营权限，只保留需求登记、状态查看和受理/分析阶段撤回；运营动作仅在管理端办理抽屉中提供。
- 已完成：本地 mock、管理端组件和个人端组件回归测试；真实后端仍未增加下文 RQ-1 至 RQ-5 契约，因此真实环境联调前不可将本地模拟当作服务端事实。
- 后续增强：运营队列统计、批量受理和可配置的候选评分阈值应在真实接口具备后补充，避免前端维护第二套规则。

## 业务闭环

```text
用户提交需求（数据需求填写结构化范围）
        ↓
运营受理：补充分析结论、优先级、可行性与风险
        ↓
数据需求：系统给出同租户相似候选
        ↓                    ↘ 保持独立
整合到主需求（共享交付，独立授权）
        ↓
分派：承接系统 + 负责人 + 交付物 + 计划日期
        ↓
进度记录（百分比、说明） → 完成/取消（结论）
```

## 本轮数据模型

```ts
export interface DataRequirementProfile {
  businessDomain: string
  dataObject: string
  scope: string
  granularity: string
  period?: string
  frequency?: string
  fields: string[]
  useCase: string
  sensitivity: 'INTERNAL' | 'SENSITIVE'
  deliveryDeadline?: string

export interface RequirementAnalysis {
  conclusion: string
  feasibility: 'FEASIBLE' | 'NEEDS_CLARIFICATION' | 'NOT_FEASIBLE'
  priority: 'HIGH' | 'MEDIUM' | 'LOW'
  risks?: string
  analyzedBy: string
  analyzedAt: string
}

export interface RequirementPlan {
  owner: string
  deliverable: string
  targetDate: string
  milestones?: string
}

export interface RequirementProgress {
  percent: number
  note: string
  recordedBy: string
  recordedAt: string
}

export interface RequirementOverlapCandidate {
  code: string
  title: string
  requester: string
  score: number
  reasons: string[]
}

export interface RequirementConsolidation {
  primaryCode: string
  role: 'PRIMARY' | 'RELATED'
  reason: string
  consolidatedBy: string
  consolidatedAt: string
}
```

## 真实接口联调台账

当前 Java 后端只提供无参 `POST /requirements/{code}/analyze`、简单 `assign`、无参 `progress` 和通用 `plan` JSON；以下契约是前端 mock 落地后必须联调的新增项：

| 编号 | 后端需提供的能力 | 目的 | 优先级 |
| --- | --- | --- | --- |
| RQ-1 | `POST /requirements/{code}/analyze` 接收分析结论、可行性、优先级、风险与操作人 | 分析有事实而非仅状态；在现有动作路径上扩展请求体 | P0 |
| RQ-2 | `GET /requirements/{code}/overlap-candidates` 返回同租户候选、评分、理由和不可整合原因 | 让管理员基于证据整合需求 | P0 |
| RQ-3 | `POST /requirements/{code}/consolidations` 创建主从整合关系并记录操作审计 | 共享交付但保留原需求和授权 | P0 |
| RQ-4 | 分派、计划、进度请求支持负责人、交付物、目标日期、里程碑、百分比和说明 | 交付可管理、过程可追溯 | P0 |
| RQ-5 | 响应返回统一 `events` 时间线和 `consolidation` 关系 | 前端不靠状态反推业务历史 | P1 |

**验收标准：** 两名同租户用户提出范围相近的数据需求时，运营人员能看到可解释的候选和匹配依据；整合后两人原需求仍分别可见，主需求统一承接交付，且每人仍需走自己的数据授权；分析、分派、进度和结项均能显示操作事实与时间。
